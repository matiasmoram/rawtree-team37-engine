### P0-2. Takeover only knows its own shard layout, so changing the number of shards creates duplicate writers. [V]

- **Code.** `engine/live.py@0140161:468-481`. The pid file is `live.pid` when there is one shard and `live_{i}_of_{n}.pid` otherwise. A new runner kills only the process in *its own* file.
- **What happened.**
  - 17:07:58: an unsharded run took over `live.pid`.
  - 17:08:13: shards 0/2 and 1/2 started. They did not stop it because their pid files were different.
  - Three writers ran from 16:09 to 16:13 UTC. Every request got 2.0-2.05 rows per minute (180/180 requests had 2 or more rows). `runner_health.json` showed PID 16164 with `shard_count: 1` answering about 180 requests/min while each shard answered about 90.
- **Effects.**
  - Requests that dropped late rose to about 6-9% per process, against 0.2% for a single writer from 17:02 to 17:08 [V counts]. The cause is contention [I].
  - Per-model leaderboard results for that window are ambiguous.
  - Skibidy's `observe()` would learn from its own proposal even when another writer's list was the one shown [I].
- **Feedback.** It still showed `served_by=team` for the duplicated requests. Duplicates did not cause `missing` [V]. Which row the judge scores is unknown.
- **Minimal fix (in `takeover()`).** Kill the process in every `logs/live*.pid` whose shard set overlaps ours. A file overlaps when its count differs from ours, or its count matches and its index matches. Skip the process's own PID. Delete pid files whose process is gone. Example:
  ```python
  m = re.fullmatch(r"live(?:_(\d+)_of_(\d+))?\.pid", f.name); i, c = (int(m[1]), int(m[2])) if m[1] else (0, 1)
  overlaps = c != self.shard_count or i == self.shard_index
  ```
- **Runtime alarm.** In `reporter()`, read the other `runner_health*.json` files. If one was updated in the last 120 s and overlaps, log an ERROR.
- **Team rule.** A change of shard count means restarting all shards. For the final round, one writer and no shards is simpler.

### P1-4. After any outage, the poller ranks the stale backlog before fresh requests. [V]

- **Code.** `live.py@0140161:199` polls `ts > watermark - 8s` in ascending ts order. Line 216 then ranks every row, however old. Only the pusher drops late rows.
- **Evidence.** Between 17:20:38 and 17:21:38: answered +543, pushed +153, dropped_late +390. About 2.5 minutes of requests were ranked, partly with LightGBM, and all were thrown away. This delayed the fresh ones.
- **Minimal fix.**
  - In `poller`, before `self.answer(req)`: if `time.time() + self.clock_offset - req.ts.timestamp() > DEADLINE - 0.3`, count the request as late, advance the watermark and `continue`.
  - Clamp the lookback to `since = max(watermark - 8s, server_now - 4s)`.

### P1-5. Push retries after a read timeout create duplicate rows; very short read timeouts churn connections. [V rows / I latency]

- **Code.** `live.py@0140161:331-332` sets the insert timeout to `remaining - 0.1`. The log shows read timeouts of 0.13-0.40 s.
- On any non-4xx error, lines 357-359 put the batch back in the outbox. If the server had already committed it, the request gets another row.
- **Evidence.** With a single writer at 16:16-16:17 UTC there were 6-8 requests per minute with 3-5 rows of the same version. Each timeout also drops the TLS connection, so the next push pays a new handshake and DNS lookup [I].
- **Fix.**
  - Re-queue only on errors raised before the request was sent: `requests.ConnectTimeout`, DNS failures, or a refused connection.
  - On `requests.ReadTimeout`, count the result as `push_unknown` and do not retry. The lab submitter already does this.
  - Use a read timeout of `max(1.0, remaining)`.
  - Port the bounded push semaphore from the fix branch (8ef9e59).

### P2-7. Arm assignment and shard ownership use the same hash. [V]

- **Code.** `arm_bucket` (`live.py:65-66`) and `request_bucket` (`experiments.py:18-21`) are both `int(md5[:8], 16) % n`.
- With 2 shards, shard 0 only ever sees even arm buckets. An arm share of odd width therefore splits unevenly. For example, `cf-v1:15` would get 16% on one shard and 14% on the other.
- **Fix.** Salt the arm hash, for example `md5(b"arm:" + rid)`. Change it only at a restart boundary, because it reshuffles which arm serves which request.
